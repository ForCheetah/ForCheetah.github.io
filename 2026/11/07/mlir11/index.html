# 前言

本篇是学习 MLIR 中的 Transform Dialect 的第五篇，主要讲的是如何在 Transform Dialect 中通过 “匹配操作（Match Operations）” 来自动发现和选择 payload IR 中需要变换的操作。内容来自 MLIR 官方教程 《Chapter 4: Matching Payload with Transform Operations》。
相关链接： LLVM Project ，MLIR 官方文档，MLIR 官网教程。
作为初学者，错误在所难免，还望不吝赐教。

# 简介

到目前为止，前面几章一直假设在调用转换方言解释器时，特定的负载操作由调用者识别。这可能与从方言驱动转换的理念相违背，因为转换目标必须通过解释器外部的机制来确定，例如在 C++ 中以编程方式调用解释器，或如前几章所示通过传递参数。
在前几章中，Transform Dialect 脚本假设 payload 中要变换的操作是由调用者在外部指定的。我们先以第一章的例子回顾一下这个调用者外部手动指定，以下是 Transform 脚本的入口签名：

这里有三个参数，% arg0 !transform.any_op 第一个参数，通常是 pass root；% arg1 !transform.op<"linalg.matmul"> 第二个参数，期望绑定到 linalg.matmul；% arg2 !transform.op<"linalg.elementwise"> 第三个参数，期望绑定到 linalg.elementwise。
调用者通过指令手动调用， debug-bind-trailing-args=linalg.matmul,linalg.elementwise 。

debug-bind-trailing-args=linalg.matmul,linalg.elementwise 把 Transform 脚本 @__transform_main 的尾部参数（trailing arguments）依次绑定到 payload 中匹配给定名字的操作上。
绑定好之后，可以从 state 中取出来，即后续通过 auto payload = state.getPayloadOps(getCall()); 取出。 如果没有手动绑定，state 里就是空的。
总结来说，debug-bind-trailing-args 是外部绑定，把 @__transform_main 的尾部参数关联到 payload 操作；apply 里的 for (Operation *payloadOp : payload) 是消费已经建立好的关联；没有绑定，state.getPayloadOps (...) 返回空，循环不执行。

这算是一种临时的、根据操作名进行的匹配，与 Transform Dialect 的设计理念不符 (变换应该由 dialect 内部驱动，而不是依赖外部机制)；增加使用成本 (C++ 交互复杂，认知负担大)。因此 Transform Dialect 引入了一类特殊的操作 ——Match Operations，用于在 payload IR 中自动匹配符合条件的操作。

# Matching Chains of Operations

上面的匹配器仍然很 naive，它仍然是靠操作名称匹配 payload root 下所有某种类型的操作。这些操作可能彼此无关，比如属于不同函数；即使在同一函数里，如果有多组这样的操作，也无法区分。
也就是说，只按操作名匹配，无法区分操作之间的依赖关系，也无法区分多组同名操作。
具体来说，上一节的 @match_elemwise 会匹配到： 那个 elementwise；<max_signed> 那个 elementwise；但它们只是 “名字都叫 linalg.elementwise”，并没有表达出操作链关系：

现实中我们想要的匹配是：一个 matmul 产生的结果被一个 elementwise 使用，而这个 elementwise 的结果又被另一个 elementwise 使用。也就是说，要匹配的是一组有 use-def 依赖关系的操作，而不是 “所有同名操作”。
所以需要一个新匹配器 @match_matmul_elemwise

其关键在于从后往前匹配，从 use-def 链的最后一个操作开始，往回找。为什么往前匹配呢：因为一个操作数（use）只有一个定义（definition）；但从一个定义出发，可能有多个 use；所以往回找是确定的、唯一的，往前找会分叉。
get_producer_of_operand 本身会检查操作数是否存在，不存在就失败，匹配器整体失败。
匹配器逐级检查，最后返回三个句柄。即使 payload 里还有其他 elementwise 和 matmul，这个匹配器也只返回有依赖关系的那一组；它返回的是三元组（matmul, middle, last），而不是按发现顺序返回一堆操作。

所以需要一个更通用的匹配操作，如果任意一个操作数满足嵌套匹配条件，就算成功；同时返回匹配到的操作数位置。

一个新的 Transform 操作，HasOperandSatisfyingOp：

MatchOpInterface 表示标记这是 Match Operation，不修改 payload。
这个接口没有额外方法，只是一个验证契约，表示这个操作是用于匹配的，不会试图变换 payload。
核心逻辑在 apply 里，思路是：遍历 payload 操作的所有操作数，对每个操作数，把嵌套匹配体执行一遍；如果所有嵌套匹配都成功，就认为这个操作数匹配成功，返回它的位置和 yield 出来的值。

根据惯例，实现 MatchOpInterface 的操作不得修改有效载荷 IR，因此必须明确指出其仅读取操作数句柄和有效载荷作为其效果。

此操作现在可以被包含在转换方言扩展中，加载并用于我们的匹配器。具体来说，我们将使用它来表示示例中 “max” 逐元素操作的任一操作数，均可由前一个逐元素操作生成。为简化起见，前一个操作仍需依赖矩阵乘法（matmul）来生成第一个操作数。更新后的匹配器序列如下所示。

关键变化点：用 has_operand_satisfying 替代硬编码的 % last [0]；body 里检查当前操作数是否由 linalg.elementwise 产生；成功时返回 % pos（操作数位置）和 % middle（匹配到的 elementwise）；后面的 matmul 检查仍然用 % middle [0]，为简单起见保留。
这实现了预期的效果，并使 max (add (matmul (...), bias), 0) 和 max (0, add (matmul (...), bias)) 的结果保持一致。因为 has_operand_satisfying 不关心是第几个操作数，只关心有没有一个操作数满足条件。
% pos 值是转换方言中的参数，用于存储在转换应用过程中已知为常量的实体列表。通常情况下，参数为数值，但一般可以是任何 MLIR 属性。这里 % pos 是！transform.param，存的是匹配到的操作数位置。后续可以根据它区分不同的匹配组。

用 transform.foreach_match 演示独立匹配。

遍历 % root 关联的 payload 操作；对每个操作执行 @match_matmul_elemwise ；如果匹配成功（没有 silenceable failure），调用 @print_matmul_elemwise ，把 yield 出来的值作为参数传入；如果匹配失败（silenceable failure），静默它；definite failure 照常立即传播。
@print_matmul_elemwise 会用 % pos 参数区分两组匹配。这样就能演示：不同组的操作可以独立匹配、独立处理。

# Matchers for Inferred Features

前几节匹配器仍有局限，它们比较基础，主要依赖操作名和 use-def 链。用 API 或声明式重写规则也能实现类似效果，有时甚至更简洁。
Transform Dialect 真正的威力在于：可以匹配 payload 的 “推断特征”—— 那些不是操作属性、也不是 IR 组件之间简单关系的性质。这些特征无法通过声明式方式表达，需要实际分析操作的结构、属性、body 等。
