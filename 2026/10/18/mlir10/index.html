# 前言

本篇是学习 MLIR 中的 Transform Dialect 的第四篇，本章主要讲的是 MLIR Transform Dialect 的进阶用法，核心围绕如何用更规范、更类型安全的方式编写 transform 操作，以及如何定义自己的 transform 类型。内容来自 MLIR 官方教程 《Chapter 3: More than Simple Transform Operations》。
相关链接： LLVM Project ，MLIR 官方文档，MLIR 官网教程， 《Chapter 0: A Primer on “Structured” Linalg Operations》。
作为初学者，错误在所难免，还望不吝赐教。

# 简介

Transform 操作中的重复模式。
在 Transform Dialect 中，很多 transform 操作都有这样的特点：对 handle 关联的每一个 payload 操作单独应用同一个变换，并且要求这些 payload 操作必须是某种特定类型。例如：把每个 func.call 的被调用者改成另一个符号；给每个 scf.for 加上某个属性；把每个 linalg.matmul 替换成自定义实现。如果每个这样的操作都手写完整的 apply 方法，就会出现大量重复代码：

这些步骤 —— 验证类型、遍历 payload、合并结果 —— 是完全模式化的，应该由框架自动完成，而不是每个操作都重复写。
MLIR 提出两个机制来解决这个问题。

1. 用 Transform 类型收窄操作数约束

原本 handle 的类型是宽泛的 TransformHandleTypeInterface，它可以指向任意 payload 操作。现在改为更具体的： Transform_ConcreteOpType<"func.call">:$call 。
这表示：这个 handle 只能关联 func.call 类型的 payload 操作。如果实际关联的不是 func.call，在验证阶段就会失败，不需要在 apply 里手动检查。
这样做的好处：类型安全：约束写在 ODS 定义里，而不是散落在 C++ 实现中；提前失败：不满足条件的 payload 在验证阶段就报错，而不是运行到一半才失败；
代码更简洁：applyToOne 的第二个参数可以直接写成 func::CallOp，不需要 dyn_cast。

2. 用 TransformEachOpTrait 自动生成 apply 骨架

TransformEachOpTrait 是一个 trait，它告诉 Transform dialect，这个操作会对每个 payload 操作单独应用一次，你（框架）帮我生成 apply 方法的骨架。
框架自动完成的事情包括：验证：检查操作数 handle 是否有效；遍历：对 handle 关联的每个 payload 操作调用一次 applyToOne；结果合并：把每次 applyToOne 产生的结果按顺序合并到最终的结果 handle 中；
失败处理：如果某次 applyToOne 返回失败，按规则传播。

# Defining a Transform Type

上一节用 Transform_ConcreteOpType<"func.call"> 把 handle 约束为具体的 func.call 操作。但有时我们想约束的不是某个具体操作，而是实现了某个接口的一类操作。

# Operand Consumption

当 transform 操作会 “消费” 操作数 handle 时，如何正确定义和实现这个操作呢？
前面 ChangeCallTargetOp 只是修改已有的 func.call（改被调用者），操作数 handle 之后还能继续用，所以它是只读操作数。如果我们现在将原有的 func.call 重写成自定义操作 my.mm4；原来的 func.call 会被 erase 掉，新的 my.mm4 被插入。
这种情况下，操作数 handle 指向的原操作已经不存在了，不能再被后续 transform 使用；所以这个 handle 被消费（consumed）了；同时变换产生了新的 payload 操作，需要返回一个新的 handle 指向它。
接下来定义一个新的 Transform 操作，CallToOp，相对于 ChangeCallTargetOp “修改已有 func.call 的被调用者符号，操作数只读，之后还能继续用”，CallToOp “把 func.call 替换成自定义操作 my.mm4，操作数被消费。”

% transformed 是一个新的 handle，它指向 payload IR 里新产生的 my.mm4 操作。那么 CallToOp 这个 Transform 操作为什么需要一个指向 my.mm4 操作的句柄呢？
假设 CallToOp 不返回任何结果，只是把 func.call 替换成 my.mm4，然后就结束了。那么：payload IR 里确实多了一个 my.mm4；但 transform 脚本里没有任何东西 “知道” 这个新操作的存在；后续的 transform 操作无法再对新产生的 my.mm4 做任何事。
也就是说，这个新操作就 “失联” 了，你只能靠它自己存在于 payload IR 里，但 transform 流程无法继续操作它。
因此，CallToOp 必须返回一个新 handle % transformed，指向新产生的 my.mm4。

和前面小节一样，上述操作需要实现 applyToOne () 函数。

失败处理：如果 rewritten 为空，说明改写失败；此时 payload IR 可能已经被不可逆地修改了，所以用 emitDefiniteError () 发出确定性失败（definite failure），而不是 silenceable failure。
结果关联：把新产生的操作 rewritten push 到 results 列表；applyToOne 要求每个结果 handle 在每次应用中恰好对应一个 payload 实体；trait 会把所有应用的结果合并，关联到最终的结果 handle $transformed。

getEffects 方法

consumesHandle (getCall (), effects) : 操作数 handle $call 被消费，之后不能再使用
producesHandle (getTransformed (), effects) : 结果 handle $transformed 被产生
modifiesPayload (effects) : payload IR 被修改
这些内存效果信息对 interpreter 很重要：它知道哪些 handle 在操作后失效，哪些是新产生的；可以做正确性检查，比如防止使用已消费的 handle。

最后，教程提到结果关联规则。
1. 成功时必须为所有结果指定实体
成功返回时，每个结果 handle 都必须有对应的实体列表；即使列表为空，也要显式设置；否则会触发断言（assertion）。
2. 失败时解释器自动填充空列表
如果操作失败，尚未定义的结果 handle 会被自动关联到空列表；这样后续使用这些 handle 时不会出错，只是关联不到任何 payload。

那么，当一个 transform 操作有结果 handle，但这次变换不想让这个结果指向任何 payload 操作时，该怎么办？
applyToOne 的语义是：对每个 payload 操作应用一次，每次应用为每个结果 handle 产生恰好一个 payload 实体。那想让结果 handle 关联空列表呢？
假设有一个 transform 操作，它接收一个非空的 handle，但变换后不产生任何新的 payload 操作，结果 handle 应该关联空列表。这时候 applyToOne 就不能使用了，需要直接实现 apply 方法。
